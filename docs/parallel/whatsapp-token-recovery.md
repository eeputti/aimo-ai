# WhatsApp-tokenin katkos ja uuden version käyttöönotto 14.11.2026

Tämä on Eeliksen **Korjaa WhatsApp-tokenin vanheneminen** -chatin raportti. Käyttäjä pyysi korjaamaan klo 22 katkenneet puhelinvastaukset, vanhan 4749-palvelinversion ja varademon varmentamattoman tilan. Meta, paikalliset salaiset asetukset ja 4749-palvelimen ylläpito kuuluvat tälle käyttöönottotyölle. Muiden varaamaa lähdekoodia ei muutettu.

## Korjaus valmis: oikea puhelinviesti ja vastaus varmennettu

- Alkuperäinen käyttöönottotyö korjasi käyttäjän erikseen hyväksymän **Test Messaging Account → Full access** -resurssioikeuden. Sama aiemmin luotu messaging-only SYSTEM_USER-token alkoi tämän jälkeen lähettää: lukukuittaus 200 ja yksi tallennettu tervehdys 200 / Meta-viestitunniste klo 22.57.20. Käyttäjä vahvisti tervehdyksen saapuneen; tämä vaihe on dokumentoitu commitissa `587ae63` / yhdistämisessä `6db19a3` ja `docs/parallel/1.md`:ssä. Uutta tokenia tai management-scopea ei tarvittu.
- **Tämän chatin credential-reload klo 23.00:** vanha PID 47387 pysäytettiin hallitusti `SIGTERM`:llä, portin vapautuminen todettiin ja sama `27ee93b5ef864f9434f65293487742d511b3dff2` -snapshot käynnistettiin samalla `deploy/whatsapp/start.mjs`-komennolla. Uusi **PID 59831**, hallintatyökalun istunto **11869**. Ei toista workeria, uutta tokenia, Meta-ohjausta tai uudemman API-koodin käyttöönottoa. `.env` ja `.env.whatsapp` ovat edelleen linkkejä samoihin nykyisiin asetuksiin; toimiva token latautui uuteen prosessiin.
- **Tietojen säilyminen varmennettu:** kaikkien viiden kannan jokaisen sovellustaulun lukumäärä täsmäsi ennen käynnistystä ja sen jälkeen. Koko members-taulun hash täsmäsi. Muun muassa 2 jäsentä, 29 jonoriviä, 3 luonnosta, 25 vuorotulosta, 2 työkalutarjousta, gatewayn 1 tilaus ja 14 audit-riviä säilyivät. Neljää aiempaa epäonnistunutta vastausta ei palautettu jonoon. Paikallinen ja julkinen `/healthz` palauttivat **200 / ordering-demo**.
- **Oikea uusi viestiketju:** käyttäjän klo **23.01.56** lähettämä kananmunia ja kermaa koskeva viesti saapui uuden workerin jonoon, eteni ensimmäisellä yrityksellä `processing` → `done`, `error=null`, ja molemmilla kahdella vastausosalla on Metan hyväksymä viestitunniste. Tästä chatista ei tehty manuaalista vastauslähetystä tai webhookin simulointia.
- **Käyttäjä vahvisti tässä chatissa: vastaus tuli WhatsAppiin.** Tämä varmentaa uuden tokenin sekä oikean puhelin → webhook → käynnissä oleva worker → Meta → puhelin -ketjun. Puhelimen typing-pisteiden näkyminen ei sisälly tähän käyttäjän kuittaukseen; selaimen pisteet varmennettiin aiemmin.
- Paikalliset salaisuuksia sisältämättömät ennen/jälkeen-tulokset ovat `/private/tmp/aimo-whatsapp-ops/credential-reload-before.json` ja `credential-reload-after.json`. Kantoja, avaimia, numeroita tai viestisisältöjä ei lisätä Gitiin. Alla ovat vianrajauksen aiemmat välivaiheet.

## Token ja katkoksen tarkennus

- Metan `debug_token` palautti HTTP 200: tokenin tyyppi `USER`, oikea sovellus, `is_valid=false`, virhekoodi 190 ja `expires_at=1794686400`, eli **14.11.2026 klo 22.00 Suomen aikaa**. Tunnus on lyhytaikainen käyttäjä-/testitoken, ei jatkuvaan palvelinkäyttöön tarkoitettu system user -token. Päättymisaika tulee Metalta, ei sovelluksen omasta ajastimesta.
- Vanha 131005-merkintä ei kuvaa viimeisintä tilannetta. Nykyisestä WhatsApp-kannasta luettiin Metan hyväksymiä vastauksia vielä klo 21.58.23, 21.58.28 ja 21.58.34. Klo 22.03 ja 22.11 vastaanotettujen viestien lähetys epäonnistui `META_HTTP_401`:een. Metan hyväksyntä ei yksin todista toimitusta tai lukemista puhelimessa. Aiemman 131005:n korjautumisen tarkkaa syytä ei päätellä tästä.
- Ennen korjaavaa oikeuslaajennusta Metan selaimesta varmistettiin olemassa oleva `AimoDemo` / Employee ja täsmälleen kolme testiresurssia: sovelluksen kehitys/katselu/testaus, Test WhatsApp Accountin numeroiden katselu ja Messages, Test Messaging Accountin viestipohjien katselu. Tämän chatin lukutarkistuksessa oikeuksia ei muutettu. Yllä kuvattu alkuperäisen käyttöönottotyön myöhempi hyväksytty Full access ratkaisi lähetyseston.
- Uuden enintään 60 päivän system user -tokenin toimintakohtainen hyväksyntä pyydettiin käyttäjältä ennen `Generate token` -painallusta. Edellisen käyttöönottotyön automaattinen hyväksyntätarkistus oli estänyt juuri tämän uuden credentialin luonnin. Käyttäjä hyväksyi tässä chatissa nimenomaisesti 60 päivän rajatun tokenin, paikallisen tallennuksen ja käyttöönoton. Tämän jälkeen havaittiin alkuperäisen `Jatka WhatsApp-käyttöönottoa` -chatin olevan jälleen aktiivinen ja jo luoneen saman AimoDemo-tokenin; tässä chatissa ei luotu toista tokenia.
- **Uusi token varmennettu itsenäisellä lukutarkistuksella:** `SYSTEM_USER`, oikea sovellus, voimassa, päättyy **13.1.2027 klo 22.25.29 Suomen aikaa**. Oikeudet `whatsapp_business_messaging` ja Metan automaattinen `public_profile`; hallintaoikeutta ei lisätty. `GET /me?fields=id,name` vahvisti nimen `AimoDemo`. App-kohtainen käyttäjä-ID eroaa Business Managerin system user -ID:stä, joten pelkkä näiden tunnisteiden erisuuruus ei tarkoita väärää käyttäjää. Oikean puhelinnumeron takaisinluku palautti HTTP 200 / `CONNECTED` / `VERIFIED`.
- Alkuperäiselle käyttöönottotyölle ilmoitettiin paikallisella taululla (#49) tarkistustulos. Se tallensi uuden tokenin `.env`:iin; tämän chatin itsenäinen takaisinluku vahvisti saman arvon, oikeudet 0600 ja ettei `.env.whatsapp` ohita tokenia. Tässä chatissa ei tehty rinnakkaista asetuskirjoitusta tai toista tokenin luontia.
- **Välivaiheen lähetyseste:** alkuperäisen käyttöönottotyön yksi diagnostinen lähetys palautti ensin HTTP 400 / Metan virhekoodin `10`, `metaAccepted=false`. Viestiä ei hyväksytty. [Metan virheluettelon](https://developers.facebook.com/documentation/business-messaging/whatsapp/support/error-codes) mukaan koodi 10 on puuttuvaan tai poistettuun oikeuteen tai endpointin kelpoisuuteen liittyvä virhe; se ei ole sama kuin vanhentuneen tokenin 190. Korjaava resurssioikeus ja lopullinen onnistuminen on kuvattu yllä.
- **Sovittu työnjako suoralla koordinoinnilla ja paikallisella taululla (#55–56):** alkuperäinen chatti selvitti Meta-oikeuden ja teki yhden diagnostisen lähetyskokeen. Tämä chatti teki nykyisen 27ee93b-snapshotin credential-reloadin vasta sen ilmoittaman onnistuneen lähetyksen jälkeen. Danielin uutta API:ta ei tuotu tähän token-reloadiin. Ennen klo 23 reloadia prosessi käytti vielä vanhaa tokenia, vaikka `.env` sisälsi jo uuden; tämä selitti sen aikana yhä epäonnistuneita vastauksia.
- Metan ohje: [system user -tokenin luonti ja 60 päivän voimassaolo](https://developers.facebook.com/docs/business-management-apis/system-users/install-apps-and-generate-tokens/). Tässä raportissa juuri nykyisen tokenin päättymisaika perustuu omaan API-takaisinlukuun.

## Rajat ja myöhempi ylläpito

1. Token on määräaikainen **13.1.2027 klo 22.25.29** asti. Se tulee uusia ennen sitä; automaattista uusijaa tai seurantaa ei luotu.
2. Puhelintoimitus ja kaksi hyväksyttyä vastausosaa on nyt varmennettu. Pisteiden näkyminen oikeassa puhelimessa on erillinen visuaalinen tarkistus; selaimen pisteet tai testituplan lähettäjä eivät todista Metan ilmaisinta puhelimessa.
3. Danielin myöhemmin valmistunut WhatsApp-listan siirto verkkokaupan ostosapuriin ei sisälly tämän chatin alkuperäiseen 27ee93b-snapshotiin. Ota se erillisessä sovitussa käyttöönotossa vasta sen riippumattoman varmennuksen jälkeen.
4. WhatsApp-linkin jakaminen ei poista nykyisen Metan testinumeron vastaanottajarajausta tai apurin testiasiakasliitosta. Tiimin omat numerot on vahvistettava ja yhdistettävä ennen niiden kokeilua. Kaikille avoin numero on erillinen käyttöönottovaihe.

Tokenin vanhenemisesta ja lähetysoikeudesta aiheutunut vastaamattomuus on korjattu nykyisessä 4749-palvelimessa ja varmennettu oikealla uudella viestillä sekä käyttäjän puhelinkuittauksella. Uutta seurantaa tai automaatiota ei luotu. Git säilyy valmiin koodin ja päätösten lähteenä.
